# Backup and restore runbook

This runbook returns Lumen to the last recorded operating state without placing
private runtime material in GitHub. The public repository backs up code, tests,
documentation, deterministic configuration, and history. It is not a backup of
recordings, learned preferences, runtime databases, credentials, or downloaded
research assets.

## What must remain separate

Never commit or push these items:

- `state/`, including SQLite databases, training recordings, learned models,
  downloaded datasets, research checkouts, and research environments.
- `.venv/` and generated bytecode.
- `.env`, provider credentials, Spotify tokens, GitHub tokens, private keys,
  or any exported account data.
- `~/.local/state/lumenengine/spotify-token.json`.

Keep a second, encrypted backup of the local state on owner-controlled storage.
Because recordings and learned preferences are private, do not place that
archive in GitHub, cloud sync, or a public file-sharing service.

## Record a new progress backup

1. Stop Monitor, Perform, rehearsal, training, and offline teacher jobs from the
   console. Confirm no Lumen process is writing to `state/`.
2. Update `CHANGELOG.md` with the version/date, operator-visible behavior,
   migrations, limitations, and test result.
3. Run the dependency-light project tests through the project environment:

   ```bash
   cd /home/the-system/Desktop/lumenengine
   PYTHONPATH=src .venv/bin/python -m unittest discover -s tests -v
   ```

4. Inspect the exact Git payload. The ignored lines for `state/` and `.venv/`
   are expected and must remain ignored:

   ```bash
   git status --short --ignored
   git diff --check
   git diff --stat
   ```

5. Commit and push the progress snapshot:

   ```bash
   git add -A
   git commit -m "describe the Lumen progress in this snapshot"
   git push origin main
   ```

6. For a numbered release, create and push an annotated restore tag after the
   passing commit:

   ```bash
   git tag -a v0.6.0 -m "Lumen Engine 0.6.0"
   git push origin v0.6.0
   ```

Use a new version instead of moving an existing release tag. `git log` is the
detailed update log; `CHANGELOG.md` is the human-readable operating log.

## Make the private local-state backup

The Git snapshot is safe while Lumen is running, but the SQLite/audio state
snapshot is not. Stop Lumen first. Mount an encrypted owner-controlled backup
drive, then archive the ignored state. Replace `/media/OWNER/LUMEN-BACKUP` with
the real mounted location:

```bash
cd /home/the-system/Desktop/lumenengine
backup_stamp="$(date +%Y%m%d-%H%M%S)"
tar --zstd -cf "/media/OWNER/LUMEN-BACKUP/lumen-state-${backup_stamp}.tar.zst" \
  state
sha256sum "/media/OWNER/LUMEN-BACKUP/lumen-state-${backup_stamp}.tar.zst" \
  > "/media/OWNER/LUMEN-BACKUP/lumen-state-${backup_stamp}.tar.zst.sha256"
```

If the drive itself is not encrypted, encrypt the archive before it leaves the
machine and securely remove the unencrypted copy. Back up the Spotify token
separately only when preserving the login is necessary; otherwise reconnect
Spotify after restore. Never add either artifact to Git.

## Restore the code on Ubuntu

Clone the public GitHub repository on the replacement machine, then install the
small live-system prerequisites:

```bash
sudo apt-get update
sudo apt-get install git python3 python3-venv python3-pip curl alsa-utils \
  libftdi1-2
mkdir -p /home/the-system/Desktop
cd /home/the-system/Desktop
git clone https://github.com/NoBrunch/lumenengine.git
cd lumenengine
git checkout v0.6.0
python3 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -e .
```

Use `git checkout main` instead when restoring the newest recorded update. A
release tag is safer when the goal is to reproduce a known version exactly.

Verify the dependency-light system before restoring state or touching DMX:

```bash
PYTHONPATH=src .venv/bin/python -m unittest discover -s tests -v
./scripts/lumen doctor
./scripts/lumen demo
```

Demo is virtual and must not open the USB adapter.

## Restore private runtime state

1. Keep Lumen stopped and disconnect the USB DMX adapter.
2. Copy the selected `lumen-state-*.tar.zst` and checksum from the encrypted
   backup drive to a temporary owner-only directory.
3. Verify and extract it into the repository:

   ```bash
   cd /path/to/temporary-backup-copy
   sha256sum -c lumen-state-YYYYMMDD-HHMMSS.tar.zst.sha256
   cd /home/the-system/Desktop/lumenengine
   tar --zstd -xf /path/to/temporary-backup-copy/lumen-state-YYYYMMDD-HHMMSS.tar.zst
   chmod -R go-rwx state
   ```

4. If no private-state backup exists, create an empty `state/` directory and
   let Lumen initialize new databases. Learned preferences, recordings, model
   activation, and research assets cannot be reconstructed from GitHub.
5. Reconnect Spotify from **System -> Spotify playback identity**, or restore
   its owner-only token to `~/.local/state/lumenengine/spotify-token.json`.

Research sources, models, and isolated environments can be recreated from the
pinned lock file when desired:

```bash
./scripts/setup-research provision
./scripts/setup-research verify
```

Provisioning downloads several large assets and is optional for normal live
operation. It must not be performed inside the dependency-light core process.

## Return to physical operating status

1. Run `./scripts/lumen doctor` and `./scripts/lumen audio-devices`.
2. Start the desktop console with `./scripts/lumen-ui` and use **Demo**.
3. Use **Monitor** with the actual line input and confirm PCM, clipping, beat,
   phrase, media identity, and the event log without physical output.
4. Confirm the restored room dimensions and fixture coordinates are in meters,
   axes are right-handed/Z-up, and housing rotations are intrinsic XYZ degrees.
5. Treat restored fixture profiles and calibration as records, not proof. Before
   enabling Perform on replacement or changed hardware, measure pan/tilt
   direction, zero, range, channel mapping, and physical latency again.
6. Stop Party Parrot or any other process that owns the FT232R adapter. Connect
   the adapter, issue blackout, and test one fixture/system at a safe intensity
   before full Perform mode.

The last known-good release and test outcome are recorded in `CHANGELOG.md`.
Runtime event logs in the console and local database stay private with the
local-state backup.
